# UI languages (i18n)

The dashboard speaks English by default and five more languages on request. The person picks the language in
Appearance → Language. The choice lives per browser in `prefs.lang` (localStorage), and every request sends it in
`X-SYA-Lang`, so what the server words (errors, notes) comes back in the same language.

| Tag | In the select | Catalogs |
|---|---|---|
| `en` | English | the source: every other language translates it |
| `ru` | Русский | translated from English |
| `es` | Español | translated from English |
| `de` | Deutsch | translated from English |
| `fr` | Français | translated from English |
| `zh-CN` | 简体中文 | translated from English |

All UI text, in every language including English, was written by Claude Opus 5.5. If you know a more accurate
translation or a better name for something, please suggest it: a pull request to the catalog, or a "Translation"
issue.

Every UI string is a catalog string. Text an agent reads is English and never a catalog string (see "Agent-facing
text").

Reference conversions: the shell (`web/index.html`, `web/app.js`, `web/figures.js`, `web/base.css`, the host's
pairing errors), `features/board` (page only), `features/todo` (page and server) and `features/chat` (page, server
and the core texts it shows: providers' errors and route reasons, below). Every feature is converted; `builder`
(errors kept in `builds.json`) and `approvals` (codes in a request's view) show the two later-worded cases below.
The example feature `tests/fixtures/hello` follows the same rules.

## Catalogs

```
src/see_your_agents/web/i18n/en.json            the shell and the host: keys app.*
src/see_your_agents/web/i18n/ru.json            ... es.json, de.json, fr.json, zh-CN.json: the same keys
src/see_your_agents/features/<id>/i18n/en.json  a feature: keys <id>.*
src/see_your_agents/features/<id>/i18n/ru.json  ... and the other languages
```

No manifest field: the host finds `i18n/` in a feature's `folder` by convention, as it finds `web/`.

- **Keys** are symbolic and carry the owner's prefix: `board.empty.working`, `todo.morning.sent`, `app.drawer.copy`.
  Lowercase, dots between levels, `_` inside a word: `[a-z0-9_]`. Name the meaning, not the words
  (`todo.not_running`, not `todo.supervisor_is_not_running_uv_run`).
- **Values** are plain text: no markup and none of `< > & "` (a test checks; use “ ” or « » for quotes).
- **Placeholders** are `{name}`, filled from params: `"{n} min"`, `"Sent: {text}"`. An unknown placeholder stays
  visible, so a typo shows on screen. Every translation has exactly the placeholders of its English string.
- **Plurals** are objects of CLDR categories that take the count from `{n}`:
  `{"one": "{n} day", "other": "{n} days"}`. The category comes from `Intl.PluralRules(lang)` on the page and from
  `i18n.plural()` on the server (the same CLDR rules). A plural object holds exactly the categories of its language,
  `Intl.PluralRules(lang).resolvedOptions().pluralCategories` (a test checks them against `PLURALS` in
  `tests/app/test_i18n.py`); a plain string stands for words that do not change with the count (`"{n} мин"`,
  `"{n} Tg."`). Categories per language:

  | Language | Categories | Example |
  |---|---|---|
  | en, de | `one`, `other` | 1 day, 2 days; 1 Sitzung, 2 Sitzungen |
  | ru | `one`, `few`, `many`, `other` | 1 день, 3 дня, 5 дней; `other` is for fractions (1,5 дня): write the `few` form |
  | es | `one`, `many`, `other` | `one` is exactly 1; 0 and 1,5 are `other` (0 días); `many` is whole millions only (1 000 000 de días) |
  | fr | `one`, `many`, `other` | `one` is 0 and 1, and 1,5 too (0 jour); `many` is whole millions only (1 000 000 de jours) |
  | zh-CN | `other` | 3 天 |

  `many` in es and fr never comes up for a count on screen; write it as the `other` text, with “de” after the
  number when a full noun follows it.

- **Fallback.** The page and the server merge a language over English: a key missing in `ru.json` (or any other
  language's file) shows the English string; a missing plural form falls back to `other`. A key no catalog has shows as the key itself and is logged
  once (the browser console: `i18n: no string for "x.y"`; the server log).
- **One owner per key.** A feature's catalog holds only `<id>.*` keys: `check_registry` refuses anything else, so
  no feature can shadow another's string. A feature may use shell keys (`app.*`) the shell already has, such as
  `app.bad_body` or `app.close`, but adds new strings to its own catalog, even when the words repeat.

## Page (JS)

The order of loading (`web/index.html`):

```
<head>  i18n.js → /i18n/<lang>.js       picks prefs.lang (else "en"), writes in the merged catalog: window.SYA_I18N
<body>  translate(document.body)        fills data-i18n markup
        figures.js → app.js → features  every script can call t() at load time
```

`web/i18n.js` writes the catalog script in with `document.write`, so it runs before the parser goes on: there is
no moment when the page has scripts but no strings. Its URL carries the page's `?v=<version>.<instance>`, like every
asset.

- **`t(key, params)`** (global; also `SYA.t`) returns the string in the page's language. `SYA.lang` is the language
  (`"en"`, `"ru"`, `"zh-CN"`), `SYA.langs` the choices (`{en: "English", ru: "Русский", …}`).
- **Write keys literally**: `t("todo.add")`, never `t("todo." + kind)` or a key in a variable. The consistency test
  finds keys by `t("…")` and `data-i18n…="…"`; for a key that depends on data, write a map of literal calls:

  ```js
  const COLUMN = { needs_you: t("board.column.needs_you"), working: t("board.column.working") };
  ```

- **HTML.** `t()` returns text. A string without params is safe in HTML as it is (catalog values carry no markup
  and nothing to escape). A string with params from data goes through `esc()`, like any text:
  `${esc(t("board.peer.sent", { text: p.text }))}`. Markup stays in the code around the call:
  `<b>${t("app.drawer.needs")}</b> ${esc(l.needs)}`.
- **Whole sentences.** One key per sentence or label, with placeholders inside; never glue fragments
  (`"ждёт " + what`). Word order differs between languages: `"waiting {time}"`, `"vor {time}"`.
- **Do not name a local `t`** (`(t) => …`, `const t = e.target`): it hides the global. Rename it when you convert a
  file (`task`, `el`).
- **Load time is fine.** Constants, registration labels and `figures.js` call `t()` while the script loads:
  `SYA.feature({ id: "todo", right: { button: t("todo.title"), … } })`.
- **Static markup** (`index.html`, a feature's `header` or `top`): `data-i18n="key"` sets the element's text and keeps
  its child elements in front of it (`<span data-i18n="app.tally.working"><b id="n-work">0</b>working</span>`);
  `data-i18n-title`, `data-i18n-aria-label`, `data-i18n-placeholder` set those attributes. Leave the English text
  in the markup. `translate(document.body)` runs once before `figures.js`; markup a feature inserts later is
  either built with `t()` (simplest) or passed through `translate(root)`.
- **CSS** has no strings: a `content:` text comes from an attribute the code fills,
  `content: attr(data-now)` with `data-now="${t("app.tasks.now")}"`.
- **Server texts.** `getJson(path)` and `postJson(path, body)` send `X-SYA-Lang`; a server error comes back already
  in the page's language: show `r.data.error` as it is, with a catalog fallback for "no answer":
  `r.data?.error || t("todo.failed")`. A plain `fetch` sends no language: use `getJson`.
- **Switching** the language saves `prefs.lang` and reloads the page, but only into the same server process
  (`/api/board` names the page's `instance`), as the update banner does. Nothing re-renders in place: there is no
  relabel pass to maintain, and constants may hold strings.

### Dates, times, numbers

Shell helpers (`app.js`) follow `SYA.lang`; use them instead of your own:

| Helper | en | ru |
|---|---|---|
| `ago(ts)` | `5 min`, `3 hr`, `2 days`, `just now` | `5 мин`, `3 ч`, `2 дн`, `только что` |
| `agoBack(ts)` | `5 min ago` | `5 мин назад` |
| `waited(ms)` | `5 min`, `less than a minute` | `5 мин`, `меньше минуты` |
| `when(ts)` | `Nov 3, 2:05 PM` | `3 нояб., 14:05` |
| `clock(ts)` | `2:05 PM` | `14:05` |
| `dayLabel(ts)` | `Today`, `Yesterday`, `November 3` | `Сегодня`, `Вчера`, `3 ноября` |
| `tokens(n)`, `contextText(c)` | `12K tokens`, `63% · 126K of 200K tokens` | `12 тыс. токенов`, `63% · 126 тыс. из 200 тыс. токенов` |
| `capital(s)` | `today` → `Today` | `сегодня` → `Сегодня` |

The other languages the same way: `agoBack` gives `hace 5 min`, `vor 5 Min.`, `il y a 5 min`, `5 分钟前`;
`dayLabel` gives `Hoy`, `Heute`, `Aujourd’hui`, `今天`. German spans are the short forms (`5 Min.`, `3 Std.`,
`2 Tg.`): a full noun would need the dative after „vor“ and „seit“.

`when`, `clock` and `dayLabel` use `Intl.DateTimeFormat` and `Intl.RelativeTimeFormat` (a 24-hour clock keeps
two-digit hours, a 12-hour one reads 9:05 AM). The spans of `ago`/`agoBack`/`waited` are catalog strings
(`app.time.*`) with plural forms, not `Intl.RelativeTimeFormat`: its short Russian forms add a period
(«5 мин. назад»), and the Russian UI keeps its copy.

`plural(n, one, few, many)` is the old Russian-only helper for strings still written in code; a converted string
is a catalog plural: `t("board.in_days", { n })`.

## Server (Python)

`see_your_agents/i18n.py` is stdlib only; core, the host and features may import it.

```python
from ...i18n import Problem, message, request_lang, t
```

- **`t(lang, key, **params)`**: `t("ru", "todo.too_many", n=300)`. It reads the shell's catalogs and every
  feature's (plus those of features registered from elsewhere, like the tests' `hello`).
- **The request's language.** The host reads `X-SYA-Lang` (English when it names none we have) and answers the
  whole request in it: `request_lang()` returns it in `handle_get`, `handle_post` and everything they call. Outside
  a request (a background thread) it is English.
- **Errors the page shows: `Problem`.** Raise `Problem(key, status=400, **params)` wherever the error is found, core
  included; do not format a sentence there. The host catches it and answers `{"error": <text in the request's
  language>}` with `status`. No try/except in the handler:

  ```python
  def handle_post(app, path, body, headers):
      ...
      if not isinstance(data, dict):
          raise Problem("app.bad_body")
      items, _ = apply(data)        # apply() raises Problem("todo.no_such_item", HTTPStatus.NOT_FOUND)
      return json_reply(_payload(app, items))
  ```

  `status` is the HTTP status, never a placeholder. A subclass can fix it: `class PairingError(Problem)` is always
  409 (`app/pairing.py`).
- **Agents get English.** The same `Problem` raised in an MCP tool reaches the agent as `str(problem)`: English
  (`app/mcp.py` treats it like `ToolError`). Logs get English too.
- **Words decided later.** When the text is shown later than the error happens (a background thread, a state the
  page polls), keep the exception, not its text, and word it when the page reads it:
  `message(exc, request_lang())` gives a `Problem` in that language and any other exception as it was raised
  (`features/todo/todo.py`, `_morning["error"]`).
- **Kept in a file.** An error that outlives the process (a build's in `builds.json`, a group delivery in its log)
  is kept as `{"key", "params"}` (plain JSON values) and worded when a page reads it; a plain string in an older
  record is shown as it is. The builder's `store.problem(key, **params)` / `store.worded(error, lang)`; the
  watchdog writes the same shape for its rollback reason (`builder.error.crashed`, `builder.error.no_answer`)
  without importing the builder.
- **Data holds no UI language.** What the parsers write into the index is a marker, not words: a compaction is an
  event of kind `compact` with no text, a Codex subagent without a task name has an empty description; the session
  panel words them (`app.event.compacted`, `app.event.subagent`). Rows indexed before that still carry Russian
  text until the parser version bump re-parses them; the panel words a compaction by its kind anyway.
- **Codes, not words, in a view.** A structure the page draws later (an approval request's `warn`) carries codes
  (`no_sandbox`) that the page maps to keys, as with `COLUMN` above.
- **Wrapping another error.** Put the inner text in a param, worded in the request's language:
  `Problem("todo.not_running_because", 409, reason=message(exc, request_lang()))`.
- **Converting core.** Exceptions raised deep in core (provider `SendError`s, `DeliveryError`, launch errors) carry a
  key and params the same way: make the class a `Problem` (or raise `Problem` subclasses), keep its HTTP status, and
  move its sentences to `web/i18n/*.json` under `app.` keys (core has no catalog of its own). Callers that print
  `str(exc)` keep working, in English.

### Core's words: `app.provider.*`, `app.column.*`

Core cannot import features, so what it says to the person at the page lives in the shell catalog
(`web/i18n/*.json`), under the prefix of what says it:

| Prefix | Who says it |
|---|---|
| `app.provider.*` | the provider contract (`core/providers/base.py`): the folder rule, the task, the refusals of a provider that cannot write, resume, stop, launch or fork; `app.provider.said` is a program's own words, `{text}` |
| `app.provider.claude.*` | Claude Code: routes and their refusals (`routes.py`), `claude --bg` and the fork (`launch.py`); `app.provider.claude.courier.*`, the courier's verdict (`courier.py`) |
| `app.provider.codex.*` | Codex: the `queue` route and its errors (`queue.py`), `codex exec` and its options (`launch.py`) |
| `app.column.*`, `app.new_session` | the board's column titles and the title of a live session not indexed yet (`core/sessions.py`) |

How each kind of text reaches the page:

- **Errors** are `Problem`s: `SendError` (502) and its `SendRefused` (409), `SendInvalid` (400), `SendTimeout` (504);
  `LaunchError` (502) and `RequestError` (400). `raise SendRefused("app.provider.claude.no_process")`; the class
  fixes the status. The chat's `DeliveryError` is a `Problem` too (`DeliveryError.of(send_error)` keeps the key and
  the status; `str()` is English, for the supervisor's tools).
- **A route's reason** (`Route.reason`) is a key with `Route.params`. `route.why()` words it in the request's
  language, `route.public()` (the card's `delivery`, `delivery_for`) carries it worded, and `route.refusal()` is the
  `SendRefused` that sending along a closed route raises. Code that showed `route.reason` as text shows
  `route.why()`.
- **The courier's verdict** (`courier.Delivery`) carries `error` as a key and `params`; `delivery.problem()` is the
  `SendError`.
- **Notes built per request** (`LaunchOptions.note`, `untrusted_note`, sandbox `labels`, the board's column titles)
  are worded where they are built, with `t(request_lang(), key)`: they are made in the request that shows them.
- A key that wraps another error's words takes them worded in the request's language, as above:
  `SendError("app.provider.claude.not_delivered", reason=message(delivery.problem(), request_lang()))`.

## Agent-facing text

English only, never a catalog string, never localized: whatever an agent reads must not change with the viewer's
language.

- the supervisor's prompts (`supervisor.md`, `features/supervisor/`), `MORNING` in `todo.py`, any text sent into a
  session (courier messages, group headers, the courier's sender name `Dashboard`);
- MCP tool descriptions, argument descriptions, `ToolError` texts, `app/mcp.py` instructions;
- builder prompts and anything written into a transcript.

All of them are English: the courier's prompt and its guard's refusal (`courier.py`), the reply note before a chat
message (`REPLY_NOTE` in `claude/transcript.py`), the sender name `Dashboard` (`claude/routes.py` `SENDER`, used by
`todo.py` and the builder's Rework too), the builder's prompt and session name (`Builder: <title>`) and the
approvals hook's deny message (`hook.py` `DENIED`). Transcripts and logs from before agent-facing text was English
carry it in Russian, and the code still matches that old data: the reply note and the sender «Дашборд» (`peer_text`
strips both notes, and the chat shows a message from either sender as the user's own), the supervisor's session name
«Супервизор» (`supervisor/launch.py` `NAMES`), and the group header `[Группа «…»` (`groups/feed.py`
`OLD_HEADER_START`: a closed member's answer to an old post still shows). When a string is both shown on the page
and read by an agent, make it a `Problem`: the page gets its language, the agent English.

Terminal output (`sya` commands, `sya hooks`, the watchdog) is English and never a catalog string: it has no
language choice. So are a git commit message the dashboard writes and the refusals of routes only a program
reads (the approvals hook's).

## How to add a string

1. Pick the key: `<id>.<area>.<meaning>`.
2. Add it to `features/<id>/i18n/en.json` (natural English: sentence case, plain verbs, product voice) and to
   `ru.json` (the same key; plural objects with `one`, `few`, `many`, `other`).
3. Use it: `t("<id>.key", params)` in JS, `t(request_lang(), "<id>.key", ...)` or `Problem("<id>.key", ...)` in
   Python.
4. `uv run pytest -q tests/app/test_i18n.py`: the key must exist in `en.json`, every `en.json` key must be used,
   translations may not add keys or change placeholders.

## How to convert a feature

Every feature is converted; this is the recipe for code that still has UI literals (a feature written before the
catalogs). `board` and `todo` are the worked examples.

1. Create `features/<id>/i18n/en.json` and `ru.json`.
2. JS: replace every UI literal with `t()`; move the Russian text verbatim into `ru.json` and write the English
   meaning into `en.json`. Labels in `SYA.feature({...})` too. Rename local variables called `t`. Use `getJson` for
   your GETs. Replace `plural(n, …)` with a catalog plural, local date helpers with the shell's.
3. Python: page-facing messages become `Problem(key, status, **params)` (or `t(request_lang(), …)` for non-error
   text); drop the try/except that turned an exception into `json_reply({"error": …})` when the host can catch the
   `Problem`. Leave agent-facing strings alone (above).
4. Tests: an error assertion on Russian text becomes English (the default), plus one assertion with
   `X-SYA-Lang: ru` that the Russian copy is unchanged. Assert on the `Problem`'s `key` and `params` where no
   server is involved.
5. Check the Russian UI looks exactly as before: screenshots of the same states from `main` and from your branch,
   `"prefs": {"lang": "ru"}` (`scripts/shoot.mjs`), and the English ones read naturally. Console clean (exit 0;
   a missing key is a console warning, so also grep the page for raw keys).

## How to add a language

1. **Create the files.** Next to every `en.json` (`web/i18n/`, each `features/<id>/i18n/` and
   `tests/fixtures/hello/i18n/`) create `<lang>.json`, e.g. `zh-CN.json`: the same keys in the same order, the
   values translated from English (`ru.json` beside it settles the meaning where the English is terse).
   - Keep exactly: the `{placeholders}` (reorder them as the grammar needs), keyboard keys (`Enter`, `Esc`, `R`,
     `/`: the shortcut list shows them from the code), commands (`uv run sya supervisor`, `claude --bg`), field
     names in request errors (`text:`, `session_id`), and the sender name “Dashboard”, which is what the agent
     sees.
   - Plural objects: exactly the categories of the language (the table above).
   - Plain text: typographic quotes of the language (« », „ “, “ ”), no `"`, `<`, `>` or `&`.
   - `groups.handle.supervisor`, `groups.handle.all` and `groups.handle.fallback` are @handles a person types:
     lowercase a–z (or Cyrillic), digits and dashes only, no accents or CJK (`todos`, `alle`, `tous`; Chinese keeps
     `all`). A mention with any other letter never matches.
2. **Register the name.** Add the language to `LANGS` in `see_your_agents/i18n.py` with its own name
   (`"zh-CN": "简体中文"`): that is the select's list, in order, and the languages `X-SYA-Lang` accepts. The tag is
   `ll` or `ll-RR` (`/i18n/<lang>.js` accepts nothing else).
3. **Plural rules.** Add its categories to `PLURALS` in `tests/app/test_i18n.py`. If `i18n.plural()` does not know
   the language yet, add its CLDR rules (integers and simple fractions are enough) and a row to
   `test_the_plural_rules_are_the_cldr_ones_the_page_uses`, checked against the browser's
   (`node -e 'console.log(new Intl.PluralRules("xx").select(1.5))'`).
4. **Run the tests.** `uv run pytest -q` (see "What guards it").
5. **Look at it.** Screenshots in the new language (`"prefs": {"lang": "<lang>"}` in `scripts/shoot.mjs`): the
   board, the chat, «New session», the to-do dock, the Appearance panel. Long words (German, French) and wide
   scripts (Chinese) are where buttons and chips overflow. Console clean (exit 0).

A partial translation works: a missing key shows English. A new feature ships `en.json` and `ru.json`; the other
languages show its English until someone translates it.

## What guards it

`tests/app/test_i18n.py`: the merge and the English fallback, the plural rules of every language against the
browser's (`PLURALS`), a missing key, `X-SYA-Lang` choosing the language of a handler and of a `Problem` (in every
language of `LANGS`), the page's catalog route, a feature catalog with a stray key, and the scan: every key the code
uses exists in English, every English key is used, catalogs hold only their owner's keys and nothing English lacks,
every catalog file is a language of `LANGS`, placeholders match, values are plain text, plural objects have exactly
their language's forms. `tests/features/test_groups.py`: every language's reserved @handles can be typed in a
mention.
